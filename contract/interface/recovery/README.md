# Recovery token pulls and retries

A recovery token carries an encrypted project's identity, key and optional remote hint. Import stores the key and updates the local project row before pulling. Conflict resolution and indexing read that updated row, so they use the restored key and the existing device's project settings. A fresh repository starts with an unborn branch. An existing repository can diverge from the remote after local edits. Imported pulls use the ordinary sync policy for related history: the remote version wins conflicts and a readable local card edit is preserved as a conflicted copy. Unrelated histories fail without replacing the local branch.

A recovery token records the project's ID scheme for generating new card IDs, including on an offline restore. Old tokens without a scheme fall back to UUIDv4. If the first pull retrieves a project manifest, its recorded scheme takes precedence.

On a device waiting for its first successful pull, the local project row and daemon registry entry are available. Existing data can still be read. A marker inside the Git directory keeps the incomplete project discoverable to database reconstruction. It also tells daemon startup to skip manifest backfill, so restarting cannot start an unrelated Git history. A rebuild preserves the database and reports that recovery is pending even if the profile has an older readiness marker. Retry the pull before editing a newly recovered project. The marker contains no token or key.

Android retries with its usual JNI pull after registering a device key. The daemon's ordinary, scheduled and explicit pulls use the same core completion path, and reimporting the token also retries. If the remote supplies a project manifest, recovery checks that its identity, mode and key match the token and keeps its durable settings. The live project's settings come from its local row, which import initially populates from the token. If the remote is older and has no project manifest, recovery writes encrypted settings and the privacy bootstrap after Git and index reconciliation succeed. The successful path then clears the pending marker. Recovery without a remote writes local metadata immediately. Ordinary plain sync does not enter pending token recovery.

The same transactional rebuild refreshes cards, links, tags and full-text indexes after either a fast-forward or conflict resolution. A failed index rebuild rolls back the SQLite changes and records a failed pull. Git can already be ahead of the index, so the next pull reconciles again even when Git reports that it is up to date. Git, key storage and SQLite are separate durable stores. They do not form one transaction.
